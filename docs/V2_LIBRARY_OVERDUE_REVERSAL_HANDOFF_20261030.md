# EduOS V2 Library — overdue charging and posted-charge corrections

**Implementation checkpoint:** 2026-10-30, owner branch `Ashraful`. This document records code behavior, not production approval. V1 Finance, HR/Payroll, Student and SaaS remain on their established V1 development baseline; no Finance entity was duplicated or re-created.

## Operational workflow

1. A TenantAdmin configures a **new effective-dated campus fine-policy version** through Library → Liabilities. Each policy sets non-negative BDT daily rate, whole grace days and an optional maximum BDT charge. Rate `0` disables future billable overdue assessments for that policy version. Existing policy versions are immutable in the application; a revision inserts a new row. A policy cannot be backdated. Campus search is server-paged, not capped to a fixed institute/student cohort.
2. A student borrows a physical copy. On a **late return**, the Library register can calculate an assessment quote using the policy effective **when the loan was issued** and existing at issue time (`EffectiveFrom <= IssueDate` and `CreatedAt <= BookIssue.CreatedAt`), rather than current prices or newly created policies. `max(0, ReturnDate − DueDate − GraceDays) × DailyRate`, capped by optional maximum, is server-calculated in decimal BDT. A return within grace period, zero-rate policy, absent historical policy or zero quote is **not billed**.
3. TenantAdmin records the overdue assessment using a unique request ID; amount is re-verified server-side in a serializable transaction. A second TenantAdmin independently approves posting or waives the entire charge. The LibraryLiability snapshot stores overdue days, effective policy, grace and daily rate. The unique `(TenantId,BookIssueId)` key prevents a second assessment for that loan. Historical lost/damaged copy charges remain supported.
4. Posting creates one dedicated `LIB-` fee-head `StudentInvoice`, one immutable amount snapshot `StudentInvoiceLine`, and a **balanced** posted `Journal` (debit receivable, credit income), under the same SQL transaction as the LibraryLiability approval. Finance payments, allocation and receivables continue using the **existing** V1 invoice/payment source of truth. The register and CSV show posted/settled/waived/reversed cases.
5. For an entirely **unpaid** posted charge (no payment allocation history), an administrator requests reversal with a new idempotency key, reason, date and open accounting period. A different administrator from both the reversal requester and original Library poster approves the reversed debit/credit journal. The original posted journal, invoice and lines are retained unchanged; invoice becomes `Cancelled` and Library liability `Reversed` only when balanced contra is posted atomically. Rejected requests can be resubmitted with new IDs. Part-paid/paid invoice corrections **must** follow controlled Finance refund/credit-note review; Library intentionally never deletes or discounts received money.

## Schema, safety and compatibility

- `LibraryFinePolicies` holds policy versions with tenant+campus FK, unique `(TenantId,CampusId,EffectiveFrom)`, idempotency key, effective date and decimal amount constraints. Tenant-filtered and campus-indexed policy search is server-side.
- `LibraryLiabilities` gets optional policy ID and assessed-overdue snapshots. Old Lost/Damaged records remain valid without backfill. State 4 is `Reversed`; state 3 `Overdue` uses the same existing student liability + invoice + journal, **not** a second payable table. SQL CHECK constraints prevent malformed snapshot/state combinations.
- Auth: admin-role AND LIBRARY module entitlement, CSRF on writes, tenant-bound SQL queries/foreign keys and per-browser-session invalidation. Reversal verifies the exact original source invoice, line, posted journal, two balanced GL lines, open period, historical payments, immutable request and independent reviewer.
- Migration `V2LibraryOverduePolicyAndReversal` is additive for existing data except widening an existing CHECK. Apply once in an approved deployment window after SQL backup and an anonymized restore rehearsal. Do not re-run a generated migration by hand. Older app versions cannot understand state `Reversed`/kind `Overdue` and must not serve Library finance routes during mixed-version rollout.
- **Rollback:** A schema downgrade that deletes policy or liability snapshot columns would lose data and fail on new kind/state rows. Prefer app-level feature gating/forward-fix, with SQL restore from the verified pre-deploy backup only under an approved recovery plan. Paid financial records must be reconciled before any restore.

Employee physical circulation is covered by `V2_LIBRARY_EMPLOYEE_CIRCULATION_HANDOFF_20261030.md` and does not create student invoices. **Do not claim 100% production acceptance from green unit tests alone.**
