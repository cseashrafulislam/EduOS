# Facilities parts issue — canonical Inventory trace

Scope: `Ashraful`, Facilities (#107) to canonical Inventory and Finance integration. Existing posted movements and journals are not rewritten. The Finance extension adds **only two filtered unique Journal indexes** in migration `20261103214000_FacilityPartsFinanceLineage`, with a preflight duplicate check; no new parallel stock, cost, or GL tables.

## Contract

Both `FACILITIES` and `INVENTORY` tenant modules must be enabled to create or void a facility issue. Existing Inventory posting and reversal routes remain protected by `INVENTORY`. The service also checks the Facilities entitlement when acting on a facility-source movement. API anti-forgery, cookie authentication, rate limiting and tenant isolation apply.

1. `POST /api/inventory/movements/facility-issues/{facilityRequestId}`: `TenantAdmin`, `Principal`, `InventoryManager`, `StoreKeeper`. Body: `{ "clientRequestId":"<unique GUID>", "fromLocationId":123, "reason":"Why these approved repairs need parts", "lines":[{"inventoryItemId":456,"quantity":2,"lotOrBatchNo":"LOT-A"}] }`. The client cannot select a work-order source ID, submit unit prices or move stock directly. The server resolves the **approved, active** work order by tenant and request ID, checks campus, location and tracked items, then saves a `Draft` canonical `InventoryMovement` (`SourceType=FacilityWorkOrder`, `SourceId=FacilityWorkOrder.Id`, `MovementTypeCode=Issue`). A matching retry returns the same draft; a changed payload with the same request ID returns 409.
2. `POST /api/inventory/movements/{reference}/post`: `TenantAdmin`, `Principal`, `InventoryManager` **other than the draft creator**, with current rowversion. The existing posting transaction rechecks source/campus/status, stock, lot balances and reservations. It determines actual weighted unit cost from stock; it atomically posts canonical Inventory movement and lines. Posting when cancellation is pending, during verification, or after closure is refused. Generic/manual movement creation cannot forge a facility source. Facility drafts cannot be reserved or partially fulfilled; create separately scoped issues when incremental use is necessary.
3. `POST /api/inventory/movements/facility-issues/{reference}/void`: same create roles; body `{ "rowVersion":"...", "reason":"No parts required after inspection" }`. Creator or Inventory post-authorized colleague can void **only an unposted draft**. The unchanged historical record becomes `Voided`, with time, actor and note. A posted issue must never be voided; use compensating reversal.
4. `POST /api/inventory/movements/{reference}/reverse`: existing `TenantAdmin`/`Principal` controlled reversal with reason and current rowversion **only before active Finance recognition is linked**. Once any non-rejected, non-cancelled `InventoryMovement` Finance journal exists, the generic route refuses reversal. Use the independently approved joint Finance/stock reversal described below; this prevents a stock-only amendment after Finance booking.
5. `GET /api/facilities/work-orders/{facilityRequestId}/parts?page=1&pageSize=25`: existing Facilities reader roles; campus and requester/technician visibility inherited from the Facilities workflow. Reads paged issue lines, actual posted cost, reversal links and optional Finance journal via `Journal.SourceType=InventoryMovement`/`SourceId=movement.Id`; no cost balances are stored in Facilities. State is `Draft`, `Posted`, `Voided` or `Reversed`. `GrossCost` preserves historical posted amount, `NetCost` is zero after an actual posted reversal. Finance state `Unlinked` explicitly means there is no associated journal; **posting physical parts does not invent or silently post accounting entries**.

## Workflow and backward compatibility

- Maker drafts / different Inventory poster posts / Facilities viewer sees report; the report also works for historical work orders without any parts, returning an empty page.
- The existing `/InventoryMovements/Transactions` create form exposes **Work-order parts issue** only when the current tenant has the Facilities module enabled. It uses the existing authorized location and item pickers, accepts the approved Facilities service-request ID, and sends only item, lot, quantity and reason to the server-resolved source-link API. The existing Inventory movement list contains the resulting draft for independent posting; no duplicate stock-entry page is created.
- Work-order verification refuses unresolved `Draft` or `Reserved` parts. Voiding resolves a draft. Work-order cancellation approval requires zero unresolved drafts **and** posted reversal of all issued parts. A returned-in-progress work order may have additional separately authorized issues.
- No old Facility request, work order, visitor, receipt, procurement, asset, inventory or Finance row is migrated. Existing ManualIssue, TransferDispatch, reservations, approvals, supplier invoices and general Inventory posting paths remain unchanged.
- Finance recognition is **explicit, never automatic**. The Accountant or TenantAdmin selects the open period, journal date, active BDT leaf **Expense** account and active BDT leaf **Inventory Asset** account after inspecting the posted stock issue. The service calculates the immutable posted movement cost using sum of quantity × posted cost, rounded to BDT 2 decimal places (AwayFromZero). It submits exactly two balanced lines to the existing `Journals`/`JournalLines`: Dr Repairs Expense, Cr Inventory Asset. The GL is authoritative only when `Journal.State=Posted`, not at stock posting or Finance request submission. No hardcoded account IDs, new balance table, or historical price revaluation.
- **Independent Finance approval:** A different Principal/TenantAdmin reviews the Submitted GL; original author cannot self-approve. The server verifies current source, campus access, active distinct account types, original amount, unchanged rowversion and open period immediately before posting. A rejected request may be replaced, but the filtered SQL index enforces at most one active recognition per movement. Every request uses a tenant-unique idempotency key.
- **Joint reversal:** Accountant/TenantAdmin requests a GL reversal linked by `Journal.ReversalOfJournalId`, original posted journal ID as SourceId, a new open-period date and reason. A different Principal/TenantAdmin verifies the exact inverse Dr Inventory Asset / Cr Repairs Expense and invokes the canonical stock-ledger compensation **inside the same serializable SQL transaction**, committing both posted GL contra and posted Inventory reversal together. A failed stock check rolls back both. The original posted entry remains unchanged; both reversal records provide audit lineage. Review rejects do not affect stock. No generic reversal is allowed after active recognition.
- `GET /api/inventory/facility-parts-finance/movements` is server-paged, tenant/campus filtered. `GET .../options` dynamically searches expense and stock-asset accounts independently; `GET .../{movement}` returns journal/reversal versions. Authenticated `TenantAdmin`, `Accountant` and `Principal` can read. Mutating Finance endpoints use maker/checker roles, anti-forgery and `FACILITIES`+`INVENTORY`+`FINANCE` module entitlements. `/InventoryMovements/FacilityFinance` exposes the bilingual workflow/manual. A missing journal is `Unlinked`; genuine cross-ledger mismatch is `OutOfSync`, not silently marked complete.
- Failed/denied actions do not write ledger data. SQL transactions are SERIALIZABLE for draft creation, posting, void and reversal. Idempotency uniqueness is enforced by existing `(TenantId,ClientRequestId)` Inventory index. Location, campus and source are checked on the server. SQL deadlocks/unique races return retry/reload responses; caller reuses the same request ID after uncertain outcomes.

## Vendor service completion evidence and campus SLA priority policy

**Do not confuse a vendor booking with vendor debt.** `FacilityWorkOrder.VendorSupplierId` is the currently approved Procurement supplier selected for the maintenance visit. It proves **who was booked**, not what was invoiced, how much is payable, or whether the supplier was paid. Existing `ProcurementSupplierInvoice` and Supplier AP are goods-receipt/stock-line sourced; **never** create a fictitious stock receipt or unlinked manual journal to bill a service. This track does not claim to post non-stock supplier AP, vendor payments or internal payroll costs.

### Independently verified service evidence

The Facilities workflow now recognizes three more source-linked, idempotent `FacilityWorkflowEvent` actions (no schema change, amount or GL mutation):

1. **`vendorattest`**: an active campus-authorized Facilities manager, distinct from the work-order requester and vendor booking approver, submits a 10–500 character service-completion certificate. The canonical work order must have a verified supplier booking, an actual `StartedAtUtc`, a `CompletedAtUtc`, and a current `PendingVerification` or `Closed` state. The latest technician `complete` action must be newer than any `return` for correction.
2. **`vendorverify`**: a different active Facilities approver independently verifies the **latest** attested completion with a reason, matching rowversion and unique command UUID; receipt/payment amounts and GL cannot be inferred from this decision.
3. **`vendorreturn`**: an independently authorized approver returns inadequate service evidence for correction. The manager may resubmit a new attestation, leaving earlier event history immutable. Vendor evidence is not automatically approved merely because work-order closure or supplier booking was approved.

A later technician `return` invalidates the previous vendor certificate. The bounded work-order list and source-linked response show `VendorAcceptanceStateCode = None / Submitted / Returned / Verified / Stale`. A fresh technician `complete` and new independent attestation/review are required before the current completion can be treated as verified. State is derived from immutable events, not copied into a parallel mutable vendor-acceptance table. Existing GL, stock, supplier invoice and payment rows are not touched by these actions.

### Optional priority-based campus SLA defaults

Existing `TenantSettings` remains the single effective SLA policy source, using `Facilities.SlaHours.{Priority}.{CampusId}` with `Priority` exactly `Low`, `Normal`, `High` or `Urgent`. A configured value is an integer **1–720 hours**, not sensitive. A missing key preserves the existing manual UTC deadline. Malformed/sensitive values fail closed. Managers can request `GET /api/facilities/work-orders/{id}/sla` only for an authorized `Submitted` request they did not create. A protected private-session response previews `RecommendedDueUtc`; the bilingual UI prepopulates it **only if the deadline is still blank**, never overwriting an operator's date or accepting a stale/foreign response. The server re-evaluates the policy inside a short SQL `SERIALIZABLE` triage command when the client submits no date. The actual triage stores the **single authoritative SLA due UTC** on `FacilityServiceRequest.SlaDueAtUtc` with a source-linked reason. Explicit legacy manual dates, audit message and command replay remain backward compatible. No timer/queue or fabricated escalation is introduced; existing overdue dashboard/manual escalation continues.
