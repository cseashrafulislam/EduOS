# Facilities parts issue — canonical Inventory trace

Scope: `Ashraful`, Facilities (#107) to Inventory integration. This is an **additive application-only change**; no new stock/Finance table or EF migration is required. Existing posted movements and journals are not rewritten.

## Contract

Both `FACILITIES` and `INVENTORY` tenant modules must be enabled to create or void a facility issue. Existing Inventory posting and reversal routes remain protected by `INVENTORY`. The service also checks the Facilities entitlement when acting on a facility-source movement. API anti-forgery, cookie authentication, rate limiting and tenant isolation apply.

1. `POST /api/inventory/movements/facility-issues/{facilityRequestId}`: `TenantAdmin`, `Principal`, `InventoryManager`, `StoreKeeper`. Body: `{ "clientRequestId":"<unique GUID>", "fromLocationId":123, "reason":"Why these approved repairs need parts", "lines":[{"inventoryItemId":456,"quantity":2,"lotOrBatchNo":"LOT-A"}] }`. The client cannot select a work-order source ID, submit unit prices or move stock directly. The server resolves the **approved, active** work order by tenant and request ID, checks campus, location and tracked items, then saves a `Draft` canonical `InventoryMovement` (`SourceType=FacilityWorkOrder`, `SourceId=FacilityWorkOrder.Id`, `MovementTypeCode=Issue`). A matching retry returns the same draft; a changed payload with the same request ID returns 409.
2. `POST /api/inventory/movements/{reference}/post`: `TenantAdmin`, `Principal`, `InventoryManager` **other than the draft creator**, with current rowversion. The existing posting transaction rechecks source/campus/status, stock, lot balances and reservations. It determines actual weighted unit cost from stock; it atomically posts canonical Inventory movement and lines. Posting when cancellation is pending, during verification, or after closure is refused. Generic/manual movement creation cannot forge a facility source. Facility drafts cannot be reserved or partially fulfilled; create separately scoped issues when incremental use is necessary.
3. `POST /api/inventory/movements/facility-issues/{reference}/void`: same create roles; body `{ "rowVersion":"...", "reason":"No parts required after inspection" }`. Creator or Inventory post-authorized colleague can void **only an unposted draft**. The unchanged historical record becomes `Voided`, with time, actor and note. A posted issue must never be voided; use compensating reversal.
4. `POST /api/inventory/movements/{reference}/reverse`: existing `TenantAdmin`/`Principal` controlled reversal with reason and current rowversion. The reversing movement has `ReversalOfMovementId` linking to the original and affects the same canonical stock ledger.
5. `GET /api/facilities/work-orders/{facilityRequestId}/parts?page=1&pageSize=25`: existing Facilities reader roles; campus and requester/technician visibility inherited from the Facilities workflow. Reads paged issue lines, actual posted cost, reversal links and optional Finance journal via `Journal.SourceType=InventoryMovement`/`SourceId=movement.Id`; no cost balances are stored in Facilities. State is `Draft`, `Posted`, `Voided` or `Reversed`. `GrossCost` preserves historical posted amount, `NetCost` is zero after an actual posted reversal. Finance state `Unlinked` explicitly means there is no associated journal; **posting physical parts does not invent or silently post accounting entries**.

## Workflow and backward compatibility

- Maker drafts / different Inventory poster posts / Facilities viewer sees report; the report also works for historical work orders without any parts, returning an empty page.
- Work-order verification refuses unresolved `Draft` or `Reserved` parts. Voiding resolves a draft. Work-order cancellation approval requires zero unresolved drafts **and** posted reversal of all issued parts. A returned-in-progress work order may have additional separately authorized issues.
- No old Facility request, work order, visitor, receipt, procurement, asset, inventory or Finance row is migrated. Existing ManualIssue, TransferDispatch, reservations, approvals, supplier invoices and general Inventory posting paths remain unchanged.
- Finance expense/account mapping is deliberately not fabricated: adding GL recognition requires a separately approved posting policy that resolves debit expense account, credit stock asset account, accounting period, campus and reversal treatment. Until then `Unlinked` is visible to operations and Finance reconciliation.
- Failed/denied actions do not write ledger data. SQL transactions are SERIALIZABLE for draft creation, posting, void and reversal. Idempotency uniqueness is enforced by existing `(TenantId,ClientRequestId)` Inventory index. Location, campus and source are checked on the server. SQL deadlocks/unique races return retry/reload responses; caller reuses the same request ID after uncertain outcomes.

It runs with the existing SQL Server Facilities filter in the migration-smoke workflow. Run `node --check EduOS.App/wwwroot/js/facilities/work-orders.js`, CI build/tests, and production-like role/campus UAT before rollout. Rollback code without deleting any posted/reversed movements; keep the additive source references for audit. This does not by itself close whole-chain issue #108 or constitute a Finance booking integration.
