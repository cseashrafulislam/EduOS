# Institutional Accounting: verified architecture and reporting boundaries

## Canonical accounting source

- The only institutional financial ledger is `Journals` + `JournalLines` + `Accounts`, scoped by `TenantId`. Financial statement reports must read **Posted and Reversed** journals together because a reversal is an independent compensating journal. Draft/rejected/cancelled journals do not contribute to posted balances.
- Fee invoices/receipts, admissions, procurement supplier invoices/settlements, payroll, facility service bills and assets retain their **operational source/subledger history**. A source transaction must post to the canonical GL exactly once under its existing idempotent workflow; it must not be summed directly together with a GL entry in income, cash or balance statements.
- `BankAccounts.AccountId` is an explicit account mapping and may be used for Bank Book and Bank Liquidity. `Accounts` currently has **no explicit Cash-in-Hand, cash-equivalent, fund, cost-centre or cash-flow-activity classification**. An account name or account-code prefix is not authoritative for these classifications.
- Historical journals cannot be edited or deleted for reporting convenience. For incorrect postings use the existing controlled approval and compensating-reversal workflows; run source-to-GL reconciliation before any backfill.
- General Ledger now applies the same account-scoped, posted-journal integrity preflight used by its paginated activity audit. Income Statement additionally rejects malformed zero/negative/dual-sided posting lines and invalid group/non-postable accounts; a balanced grand total cannot justify invalid source lines.

## Open design decisions / release gates

**Manual Task 1 → Task 5 UI handoff (2026-11-06):** `GET /api/finance/accounting/reports/ledger/{accountId}/activity` retains its current contract and now adds per-page balance fields. Task 5 may display running balance and accurate page opening/closing in the existing bilingual Posted Activity Audit and its **page-only** CSV, without replacing the canonical journal API or implying a page subtotal is the institutional balance. The legacy full `GET /ledger/{accountId}` remains capped at 5,000 lines for compatibility; use the bounded activity endpoint for larger historical inspections until a separately reviewed paginated General Ledger UI replaces that legacy rendering. Exact-SHA SQL translation, authenticated browser and representative high-volume query-plan evidence remain required before production acceptance.

**Accrual vs. collection:** posted revenue or cost does not prove the corresponding fee/supplier amount has been paid. Use existing Fee Receivables, Payables, Bank Book and individual module settlements for outstanding and actual bank movements. Never add source invoice totals to these GL-derived income/cost totals: that would double-count. Report CSV includes only the visible page; aggregate cards reflect every matching page.

1. **Statement of Cash Flows (Operating/Investing/Financing) and consolidated Cash Book:** not valid without an explicit tenant-scoped Cash-in-Hand/Equivalent account designation, journal classification policy including cash/non-cash and internal transfers, opening-balance migration and end-to-end cash reconciliation. Bank Liquidity must not be relabelled Cash Flow. Add additive schema/configuration and independent SQL transaction fixtures before offering these statements.
2. **Fund / Department / Project budget allocation:** the new institution-wide, period-scoped approved Budget vs Actual is authoritative for the tenant's high-level income and expense plan only. Fund-specific, campus, department and project budgets still require explicit historical journal-line attribution. No guesses or double-counted inter-campus allocations. A revised institutional budget is a new immutable proposal, and only a period with no overlapping approved budget may be approved; the current interface does not amend an already approved period.
3. **Institution-wide AP liability control:** the existing Procurement + Facilities supplier aging now appears under Central Finance. It implements cutoff-specific posted-payment, supplier return and reversal rules and validates source GL links on returned pages, but it still includes fully paid/reversed invoice rows, totals only the selected page, and does not prove the aggregate AP control-account closing balance. A full-institution open-only aging and AP-to-GL control account reconciliation remain a separate release gate; it must not be replaced with a sum of both source and GL totals.
4. **GL posting coverage for every module:** execute source-to-posted-journal exception reconciliation at an exact database snapshot before declaring institution-wide totals complete. Missing or duplicate source postings must go to controlled correction; do not auto-post historical transactions.
   - The Module Posting Audit is now a safe first-line read-only diagnostic across nine existing source categories. It shows the source accounting link and validates the related posted journal on each visible page, including a tenant-scoped duplicate-source lookup. Payroll payment and procurement return credit lineages are included; GL-only supplier/bank settlement journals and other refund/reversal subflows still need dedicated matching rules. It does **not** prove end-to-end source amount mapping for all journal types (supplier price variance, payroll components and asset capitalization have different debit totals), cover all later settlement/credit/return subflows, or provide a transactionally consistent whole-database snapshot. Run specialized SQL reconciliation tests and inspect every page before marking complete.
5. **Quality:** independent .NET/SQL migration and authenticated tenant/campus browser acceptance, high-volume database paging and cross-tenant/role attempts still need CI and staging verification. JavaScript contract tests alone cannot constitute financial or production acceptance.

The existing consolidated Finance reports remain read-only and tenant-admin-scoped, and journal reporting keeps its existing GL interfaces. The institution Budget planning workflow is deliberately **not** a GL report: it adds two additive approval/snapshot tables and one separate mutation API with CSRF, independent review and rowversion guards. Its Actual endpoint is read-only and invokes the canonical reconciled income statement. Budget and bank liquidity are not substitutes for classified cash-flow reporting.
