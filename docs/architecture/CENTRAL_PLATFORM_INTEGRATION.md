## 1. Architecture decision and evidence levels

1. **Central authority** means one authoritative implementation for a shared fact or policy (for example, one posted Finance GL); it does **not** mean all operations must share a generic table or a generic status machine.
2. **Domain authority** owns its business-specific transaction, lifecycle, permissions, historical snapshots and corrections; central services consume explicitly authorized references or projections.
3. **Central read workspace** is an authorized composition over existing domain data, not another editable source of truth. Fetch in bounded, server-filtered batches; never import all modules into a shadow table just to display a dashboard.
4. **No new database, broad data merge, document renumbering, migration, generic workflow engine, queue or microservice** is approved by this document. A narrowly justified additive schema change requires separate evidence and review.

Status labels below are deliberately conservative:

| Label | Meaning | Required before calling integration complete |
| --- | --- | --- |
| **Existing core** | Canonical entity/service or shared UI exists in the inspected source. | Every claimed consumer path traced and tested, including authorization and replay. |
| **Partial adoption** | Shared foundation exists, but not all consumers or operational acceptance are demonstrated. | Consumer inventory, tests and issue-specific gap closure. |
| **Proposed composition** | Cross-module experience has not been identified as one coherent implementation. | First search existing routes/helpers; build an authorized read-side composition only if needed. |

## 4. Canonical flow contracts

1. **Financial:** Domain command → independent authorization/state/amount validation → domain transaction + one unique source-linked GL posting → commit → read-only Finance/report trace. Corrections use original-source linked contra/reversal. Domain invoice status cannot be inferred from a notification or a cached dashboard. Include one-time and partial settlement, refund and closed-period cases.
2. **Stock and assets:** Authorized PO/receipt/issue/return/Facilities action → canonical `InventoryMovement` and lines → exact source references, quantities, units, custody and any required GL → immutable posting/reversal. A procurement inventory asset debit must not become an immediate P&L expense merely because supplier payment exists.
3. **Identity:** Global Person may link to multiple institutions only through verified consent/ownership. Tenant-owned Student, Guardian, Employee, LMS and Alumni data remain siloed. Never search across or join private tenant data merely because PersonId matches.
4. **Document:** Domain holds metadata/reference → private `FileAsset` owns upload/storage lifecycle → each download/export independently validates current authorization, owner and tenant/campus/subject. Attachment existence cannot grant access.
5. **Approval/work center:** Read source-owned pending tasks under current role/campus/entitlement → show deep link → send mutation only to original domain API with original rowversion, maker/checker, CSRF and idempotency rules → re-read source after decision. No generic `Approved` flag and no cross-module auto-post.
6. **Communication:** Domain decides recipient, scope and lawful consent → central template/gateway dispatch → retry-safe delivery history and audit. Provider callback proves delivery outcome only, never fee payment, admission approval or exam result publication.

## 6. Implementation and migration rules for every central feature

1. **Trace before editing:** list all writers, readers, reports, exports, jobs and external consumers; inspect actual EF mappings/indexes, domain transitions, existing interfaces/DI and tests. Mark each centrality claim **verified**, **partial** or **not found**, with file paths and commit SHA.
2. **Choose one owner:** only one service owns each posted financial/stock transition. Other domains reference immutable source IDs and use read-only projections. Reuse existing query/authorization helpers; a new composition service is justified only for actual multi-domain reads.
3. **Define scope and invariants:** source entity/key, TenantId/CampusId/ownership, roles, module entitlement, date vs UTC timestamp, allowed state, idempotency, rowversion, source uniqueness and historical correction rules. Use decimal for amounts/quantities.
4. **Bound reads:** predicate by current tenant and permitted campus **before** joins/aggregation; project only required columns, include stable sort and page token/offset, cap page/export size. Verify actual SQL query plan/indexes with representative data. A dashboard summary must not be calculated with `GetAll().ToList()`.
5. **Protect high-risk writes:** in the existing short transaction, re-read source state/authorization, enforce independent review and unique posting/replay, commit linked canonical movement/GL once, audit without secrets. Never rely on frontend disable state or cache.
6. **Compatibility first:** add optional source links and read models only when necessary, then backfill after validated tenant/source join, deploy new readers, and retire duplicated storage only after explicit data-loss and rollback approval. No production migration or historical renumbering from this document.
7. **Verify exactly:** static contracts may catch regressions but cannot replace SQL-backed functional tests, concurrency/rollback, authenticated tenant-switch browser, export/file IDOR, real provider sandbox, representative load and institution UAT.
8. **Record ownership:** a single row in the existing master backlog states evidence, precise changed files, acceptance outcomes, known gates, QA SHA and rollback notes. Do not create parallel status boards, recurring automations or version-based mini-projects.

## 8. Central Work Center — initial implementation and handoff

**Purpose and scope:** Read-only approval references for four existing source workflows. It is an inbox shortcut, **not** a new workflow engine, a second approval status, a stock movement or a Finance posting.

| Source (`Source` in API) | Pending state | Reviewer and maker exclusion | Original owner and destination |
| --- | --- | --- | --- |
| `ProcurementRequisition` | `Submitted` | Live `TenantAdmin` / `Principal` / `InventoryManager`; `CreatedBy` must exist and differ from reviewer | Procurement requisition module (`/ProcurementRequisitions/Index?workId={id}`) |
| `ProcurementPurchaseOrder` | `Submitted`, `CancelRequested` | Same live roles; `CreatedBy` must exist and differ from reviewer | Procurement PO module (`/ProcurementPurchaseOrders/Index?workId={id}`) |
| `FacilityVisitorPolicy` | `Submitted` | Live `TenantAdmin` / `Principal`; `RequestedByUserId` differs from reviewer | Facilities visitor module (`/FacilityVisitors/Index?campusId={id}`); this link opens **campus policy workspace**, not a specific policy-change detail |
| `AccountingJournal` | Submitted *manual* journal or its submitted compensating reversal only; institution-wide `CampusId = NULL` | Live `TenantAdmin` / `Principal`, active membership, FINANCE module; maker `CreatedBy` must exist and differ from reviewer | Existing Finance journals (`/AccountingJournals/Index?reference={publicGuid}`); source detail performs its own authorization and review/rowversion checks |

**Endpoints:** `GET /CentralWorkCenter/Index` shows the role-scoped bilingual page. `GET /api/platform/work-center/pending?page=1&pageSize=25&campusId=` returns `ApiResponse<CentralWorkCenterPageDto>` with `InventoryIncluded`, `FacilitiesIncluded`, `FinanceIncluded`, and a `PagedResult<CentralWorkItemDto>` (`Source`, `SourceId`, nullable `CampusId`, optional `SourceReference`, `Reference`, `State`, `SubmittedAtUtc`, `WorkspaceUrl`). Maximum page size is **100 per request**, not a global 100-record or 5,000-record limit. Server-side count, stable ordering and paging happen before detail projections. The API and page disable caching; frontend aborts outdated requests and escapes source text.

**Data, security and compatibility:** The service checks actual current tenant (`db.CurrentTenantId`), active identity/membership, current live tenant roles, active campus access, tenant module entitlements and optional-module pilot restrictions, before unioning filtered source queries. Finance is a core module and is not hidden by the Inventory/Facilities pilot switch; `campusId` selections intentionally exclude institution-wide journals. A stale role in a cookie cannot alone grant inbox data. The system adds **no tables, migrations, alternate approval rows or mutations**. Each decision, rowversion validation, CSRF and posting remains exclusively in the existing source module. The central workspace returns source references only; users still need existing module authorization to open them. A 409 asks for refresh if source state changes during the bounded read.

**Evidence and limits:** `EduOS.Tests/Services/CentralWorkCenterServiceTests.cs` covers tenant/campus isolation, active membership/live role, maker exclusion, Finance and other module entitlements, pilot, combined counts and paging using EF InMemory. `EduOS.Tests/JavaScript/central-work-center.test.cjs` covers escaped display, allowlisted links including Finance public GUIDs and no-write controls; existing page Help tests validate the bilingual manual. `EduOS.Tests/App/SqlServerCentralWorkCenterTests.cs` now exercises the cross-module SQL `Concat`/paging, campus restriction, maker exclusion, institution-wide Finance references and live role revocation in the disposable SQL Server migration workflow. `SqlServerCentralLedgerActivityTests.cs` separately checks ordered Finance page-prefix and tenant isolation against SQL Server. **An added test is not an accepted result:** inspect the exact-SHA V1 SQL gate and full CI; authenticated browser deep links, realistic tenant-switch/SQL query-plan/load evidence and production permissions remain separate gates. Do not mark other P0/P1/P2 capabilities complete by association.

## 9. Central Institutional MIS and unbounded aggregate-only Finance totals (2026-11-06)

**Implemented backend slice, acceptance pending at this commit:** `GET /api/platform/institution-mis?fromDate=&toDate=` is a tenant-admin-only, read-only institutional overview. It requires a live active administrator role and tenant membership, `REPORTING` entitlement and a period no longer than 366 days. The API intentionally has **no campus filter**: the canonical Finance GL summary is institution-wide, and showing an institution-wide number under a campus label would be an incorrect result. It does not persist a KPI, change an approval, issue stock or post a journal. Each metric carries its exact owner/table, definition, unit, Current-vs-Period scope and entitlement availability. A disabled module is `Available=false, Value=null`, **never a fictitious zero**. No private student names or financial source details appear in the summary.

**Canonical metric owners:** active students (`Students`), active employees (`Employees`), submitted requisitions (`ProcurementRequisitions`), active asset masters (`Assets`), issued book loans (`BookIssues`), active hostel allocations (`StudentHostelAllocations`), open facility work orders (`FacilityWorkOrders`), period planned transport trips (`TransportTrips`) and posted income/expenses/net surplus from the **existing GL**. Current counts are a snapshot at request time; transport and GL are selected-period metrics. These are descriptive source counts, not interchangeable monetary amounts, attendance, utilization rates, asset carrying values or cash collection claims. Query each source with explicit tenant and undeleted filters in SQL; no full-table materialization, inferred financial postings, stock balance or shadow dashboard storage.

**Finance scaling contract:** `GET /api/finance/accounting/reports/income-expense-totals` calls `AccountingReportingService.GetInstitutionalIncomeExpenseTotalsAsync` and uses SQL sums over validated posted GL rows. It verifies historical deletion, currency, foreign-tenant lines, debit/credit line rules, per-journal balance and referenced posting accounts. Unlike the legacy **full account-row** income statement, the aggregate-only endpoint does not reject an institution solely because it has over 5,000 posting accounts. The existing paged `income-expense-details` API now reuses this aggregate integrity path while keeping its own count/filter/page SQL projection. The old full-statement API keeps its original response contract and bounded export behavior. No database schema or posting transaction changed.

**Task 5 UI handoff:** Display the supplied metric definition/scope/unit and a distinct unavailable state; do not calculate institution finance totals from StudentPayments or other domain receipts. No `campusId` picker should be attached to the institution-wide GL summary. Use existing bilingual Page Help, role/entitlement visibility, server no-store and authorized links for any presentation change. **Task 6 QA handoff:** Add SQL tenant/role switch, missing entitlement, large account/transaction distribution, corrupted posted journal and full browser acceptance. The source-level InMemory and SQL fixture additions are not production load measurements or institute UAT. Verify exact-SHA CI/SQL before declaring this slice accepted.

## 10. Central inventory Stock Position without catalog-size limit (2026-11-06)

**Owner and contract:** `InventoryMovementService.GetStockPositionAsync` remains a tenant- and campus-authorized read-only projection of **posted** `InventoryMovement`/`InventoryMovementLine` effects, not a new mutable stock quantity. Inactive tracked catalog items remain visible for history; non-stock-tracked/deleted and cross-tenant items remain excluded. `asOfUtc` is UTC-only, and lot-level negative quantity, negative recorded cost or residual cost outside 0.01 still yields 409 for *any* matching lot, not merely a requested page. `RecordedCostBalance` is historical movement cost, **not** an approved FIFO/weighted-average accounting valuation. The GET contract and DTO do not change.

**Implementation:** Apply tenant, stock-tracked and optional item search filters in SQL. Aggregate canonical signed posted movements by lot and test all matched lots for integrity in SQL. For nonzero-stock mode, derive eligible item IDs using a SQL item-level quantity aggregation before `COUNT`, stable `Code/Id` order and `Skip/Take`. Only the selected catalog page (up to 100 items) is materialized; its lot balances are fetched once from the canonical ledger, then combined into the response in memory. Zero-stock catalog rows remain visible without an aggregate left join. Never materialize a full matching catalog or issue queries in fixed batches; the historical 2,000-item 422 guard is removed. `pageSize` remains bounded at 100 for predictable response payload, independent of catalog cardinality. No migration, writable data copy, new posting rules, valuation logic or domain API changes.

**Acceptance and operations:** Unit tests cover 2,501 items, zero-stock visibility, negative lots outside the requested page, permission and UTC cutoffs. The disposable SQL Server inventory test validates that the actual provider translates the nested aggregation and paged projection, and reconciles opening movement quantity/value. Measure logical reads, query duration and query plan against realistic many-tenant lot histories; adjust tenant/item/location/date indexes only from observed plans. Existing Finance/Inventory/UI owners must reconcile source → central and central → source totals separately. CI and disposable SQL green at the exact commit are necessary, **not** sufficient for production 100% certification.

**Legacy dashboard financial privacy correction:** `GET /api/dashboard` remains available to ordinary authenticated institute members for its existing onboarding/usage view, but `MonthlyCollection` (StudentPayment receipt amount) and `TotalDues` (StudentInvoice due amount) are now nullable, visible only to a live authorized TenantAdmin. `FinancialSummaryAvailable=false` plus null values explicitly means **not authorized**, not financial zero.
