### 1.1. Canonical quota/security behavior retained from superseded SaaS handoffs

- The configured effective-plan MaxStudents/MaxEmployees limits are checked on **new active capacity** (admission conversion/import/readmission/reactivation, employee creation/reactivation) inside tenant-safe competing-write protection. Configured zero means unlimited; absence of an effective plan must not invent a quota, and existing subscription access policy still applies. Over-limit submissions return a conflict without partial import or new active records. Reducing a limit below current use never silently deletes existing students/employees.
- Private document/message storage follows configured MaxStorageMb with ownership, quota/transaction protection and failed-upload blob cleanup. Verified public applicants are tenant-bound. Limited private payment proof remains allowed for an otherwise storage-full institution so renewal is not blocked; it must not bypass privacy, file-size or pending-invoice controls. Live usage counters are **not** dated usage snapshots or financial meters. Exact runtime code and SQL tests remain authoritative; this paragraph preserves operational invariants, not proof every edge case passes today.
- Sensitive file storage and Data Protection key paths stay outside public webroot with protected backup and ACLs; see [production secrets](PRODUCTION_SECRETS.md). Treat provider activation, representative load, actual institute UAT and go/no-go as **external acceptance**, not repeated code-feature backlog.
